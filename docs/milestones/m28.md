# M28 — 404 and Fallback Pages

## Goal

Add a thoughtful not-found experience and basic fallback handling so direct links, moved paths, and future multi-page growth do not produce abrupt dead ends.

## Recommended Delivery Mode

- Lead: Haiku build pass is acceptable
- Review: Sonnet review pass for copy clarity, routing assumptions, and GitHub Pages behavior

## Dependencies

- M17 complete
- M25 and M26 recommended

## PR Scope

- `404.html`
- Shared styles or content files only as needed
- Optional updates to `README.md` or deployment notes if GitHub Pages behavior needs to be documented

## Tasks

- [ ] Create a branded `404.html` that matches the site style
- [ ] Include a short helpful explanation and clear routes back to the homepage or key sections/pages
- [ ] Ensure the page works on GitHub Pages without app-router assumptions
- [ ] If the site becomes multilingual by this point, decide on a simple fallback language strategy
- [ ] Avoid adding complex redirect logic unless there is a concrete need

## Definition of Done

- Unknown routes no longer feel broken or abandoned
- The page is visually consistent and useful on mobile and desktop
- The implementation stays simple for static hosting

## Open Questions

- If the site remains mostly single-page, should the 404 be extremely minimal or still anticipate future deep links?
